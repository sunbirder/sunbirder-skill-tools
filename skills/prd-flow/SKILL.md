# prd-flow · 八步需求文档工作流（sunbirder 版）

把一个模糊想法变成八份可交接的工件。你的角色不是"代写文档"，而是**引导者 + 撰写者 + 门卫**：提问澄清、按模板起草、用清单把关，每一步经用户确认后才前进。

方法论出处：八步骨架与工件协议源自开源 prd-flow 工作流（其上游为 Mike Cohn 用户故事、BDD GWT、INVEST、Pre-mortem 等行业共识 + superpowers brainstorming / mattpocock grilling / req2code 等 AI 协作技能的集成）；本版为 sunbirder 适配——证据标注细化为三态、工件根目录统一 `docs/reqs/`、与 discuss / completion-contract 等本机技能互链、引入术语表机制。

## 全局纪律（每一步都适用）

1. **工件落盘，文件即交接**：所有产物写入**工件根目录**下的 `<产品名>/` 子目录，文件名固定为
   `00-澄清记录.md`、`01-问题定义.md`、`02-范围说明书.md`、`03-用户故事.md`、`04-场景与状态/`（index + 模块文件）、`05-PRD.md`、`06-预演评审记录.md`、`07-任务拆解.md`。
   下游只读上游文件，不依赖会话记忆。
   **工件根目录的确定**：统一写入 `docs/reqs/<产品名>/`；项目无 docs/ 目录时先创建。用户显式指定路径时以用户为准。
   **产品目录内部分层**（定版后形态）：`04-场景与状态/` 按模块拆文件（index + F01-<模块>.md…）；`pages/` 存页面设计（PGE 编号）+ `pages/index.md` 公共组件清单；`features/` 存复杂功能级详述；`versions/` 存定版快照；`releases.md` 版本台账；`index.md` 文档地图。
2. **证据三态标注**：每条关键结论必须标注证据状态——
   - `[代码证据 <路径>]`：从代码直接读取的事实
   - `[文档证据 <路径>]` / `[数据证据 <来源>]`：文档、对话原话、统计数字
   - `[推断]`：AI 归纳，需用户点头后升级
   - 确认后的结论追加 `[用户确认 YYYY-MM-DD]` 或 `[客户确认 YYYY-MM-DD]`
   没有证据的问题不许静默跳过；"有学习动机"式的不可验证表述是 bug。
3. **确认留痕**：每步结束必须获得用户对该步产物的明确确认，并把确认状态写入 `<工件根>/<产品名>/_状态.md`（三态：`AI推断 / 用户确认 / 客户确认`）。**只口头确认不落盘视为未确认；未确认不得进入下一步。**
4. **提问协议**：每轮最多 4 个问题；每问给 2-4 个选项并附你的推荐答案（措辞让"对"= 接受推荐）；事实（代码库/文档/数据能查到的）自己查，只有决策问人。详细方法见 [references/question-playbook.md](references/question-playbook.md)。
5. **禁止代用户拍板**：优先级、取舍、边界属于用户决策。发现自己在替用户做产品决定时，停下来提问。
6. **术语表机制**：产品涉及多工件、多轮迭代时，在 `docs/GLOSSARY.md`（或 `<工件根>/<产品名>/GLOSSARY.md`）维护术语表：术语 + 定定义 + Avoid 项（易混淆词）。所有工件用词遵循术语表；新术语先入表再使用。

## 状态机与续跑

每次被触发时，先按上述规则确定工件根目录，再检查 `<工件根>/<产品名>/_状态.md` 是否存在：

- **存在** → 读出当前步与未确认项，从上次停下的地方继续；不要重问已确认的问题。
- **不存在** → 与用户确认产品名后创建，从 Step 01 开始。

`_状态.md` 格式（保持简单，机器与人都能读）：

```markdown
# prd-flow 状态 · <产品名>
当前版本：v1.0-dev
本版批次：
- 需求：<本版要做的需求组>
- 修复：<本版要修的 bug>
当前步：03
## 各步状态
| 步 | 工件 | 状态 | 确认 |
| --- | --- | --- | --- |
| 01 | 00-澄清记录.md | 完成 | 用户确认 2026-XX-XX |
| 02 | 01-问题定义.md | 进行中 | — |
## 待确认项
| # | 问题 | AI倾向 | 用户答复 | 状态 |
```

## 版本协议（版本 = 需求批次）

版本是**需求批次**，不是"每次修改"。只有两个动作会产生版本动作，版本内的日常迭代**零记录**：

| 动作 | 触发语 | 执行 |
| --- | --- | --- |
| **开版** | "开 v2.0，这版做 A/B，修 X" | `_状态.md` 登记：当前版本=v2.0-dev + 本版批次清单（需求组/修复项）；versions/ 与 releases.md 不动 |
| **版本内迭代** | 正常修改需求 | 直接改 00-07 工件本体；**不产生任何变更记录** |
| **定版** | "这版定稿/发布" | ① 整套工件（除 versions/ 外）复制进 `versions/<版本>/` ② `releases.md` 追加一行（版本/定版日期/主题/需求批次/修复） ③ `_状态.md` 当前版本翻转（去掉 -dev） ④ **翻转所有工件头部的版本行**（含 04-场景与状态/ 每个模块文件） ⑤ 更新产品 `index.md` 文档地图（各工件状态 + 当前版本） ⑥ **修快照内链接**：快照里指向产品根或快照外文件的相对链接，改为快照内相对路径或降为纯文本（相对链接换目录会变死链） |

- 版本号规则：首个定版 v1.0；小改 +0.1；范围/结构变化 +1.0；允许跳版本
- **禁止**在版本内维护逐次变更记录表；追溯靠稳定编号 + versions/ 快照
- **编号双轨约定**：故事编号 US-F<n>-<n> 使用起草期稳定 ID（只增不复用，不重编）；05-PRD 5.4 功能清单与 04-场景与状态/ 模块文件使用**归并编号** F01…（与 R 对齐），5.4 必须附「归并映射表」；04 模块文件头部同时标注归并编号与原范围编号
- 回看历史 = 打开 `versions/<旧版本>/` 原样快照；当前态永远是唯一的工作副本

## 与本机其它技能的衔接

| 场景 | 分流 |
| --- | --- |
| 用户在纠结「选 A 还是 B」的技术/方案决策，还谈不上需求 | 建议走 `discuss` 技能（轻量方案讨论）；讨论沉淀的结论可作为 Step 01 输入 |
| 需求极模糊、对方也没想清楚 | Step 01 提问可用 `superpowers:brainstorming` 的苏格拉底式一次一问 |
| 需求方有基本想法、要快速收敛 | Step 01 默认用 grilling 决策树前沿批量问（见 question-playbook） |
| Step 08 拆解出的关键任务需要可执行验收协议 | 对该任务调用 `completion-contract` 生成完成契约（outcome/verification/constraints/boundaries/stop_when） |
| 需求已定、要对既有代码清点底座能力 | 底座资产清单可参照 `doc-gen` 的项目分析产出 |
| Step 05 页面设计（PGE 工件）定稿后需要视觉稿/海报 | 对该页面调用 `frontend-design`（UI 视觉方案）或 `canvas-design`（海报/单图视觉稿）；PGE 五态与字段表即设计 brief |

## 路由

根据用户意图选择模式：

| 用户想要 | 模式 | 动作 |
| --- | --- | --- |
| 从想法开始做需求分析 | 全流程 | Step 01 → 08，逐步推进 |
| 继续上次的 | 续跑 | 读 `_状态.md`，从当前步继续 |
| 只做某一步（如"帮我写用户故事"） | 单步 | 跳到该步；若上游工件缺失，先声明假设并请用户补关键输入 |
| "评审这份 PRD" | 仅 Step 07 | 读取用户给的 PRD，跑三道闸，产出 06-预演评审记录.md |
| "拆任务/排期" | 仅 Step 08 | 读取 PRD（或用户指定文档），产出 07-任务拆解.md |

上游工件缺失时不要静默编造：把缺失项列为 🔵 待确认，向用户要最小必要输入。

## 八步总览（每步的详细规范在 references/，执行到哪步读哪步）

| 步 | 产出 | 核心规范 |
| --- | --- | --- |
| 01 澄清拷打 | 00-澄清记录.md | 决策树提问；结论标证据三态；挂起项给 Owner |
| 02 问题定义 | 01-问题定义.md | 共情五段叙事 + 一句话收口 + 证据 + 北极星/Guardrail |
| 03 范围圈定 | 02-范围说明书.md | 角色禁"user"并标注端（web/移动/小程序）；P0 ≤ 5；明确不做每条附原因 |
| 04 用户故事 | 03-用户故事.md | 三段式 + GWT（一个 When 一个 Then）；每故事 ≥3 条 AC（happy+edge+negative）；INVEST |
| 05 场景与状态 | 04-场景与状态/（模块维度）+ pages/（页面维度，含 index.md 公共组件清单） | 流程图三分支（主流程+分支+异常）；页面五态；字段表；主流程禁 if/else；每页先判交互模式再摆分区 |
| 06 PRD 组装 | 05-PRD.md | 12 节模板组装上游工件；8.0 含端列 + 主任务页面流转；🔶/🔵 内联标记；禁实现细节 |
| 07 评审预演 | 06-预演评审记录.md | 三道闸：清单机审 → Tigers 思想实验 → 四类场景走查 |
| 08 任务拆解 | 07-任务拆解.md | ≤2 故事/≤24 人时；第一刀 Walking Skeleton；追溯矩阵 ≥95% |

每步的执行方式固定为五拍：

```
① 读本文件「八步总览」该行规范 + 复制 assets 模板（见下）
② 提问/查证 → 收集本步输入
③ 复制 templates/0X-*.md 到 <工件根>/<产品名>/ 并填写（04 步建 04-场景与状态/ 目录）
④ 跑该步"核心规范/检查清单"自检（不通过就改，不通过不展示）
⑤ 向用户展示产物 + 1 个确认问题；确认后更新 _状态.md
```

## 质量门

- 每步 ④ 的自检按八步总览的核心规范逐项过，禁止凭感觉跳过。
- Step 06 产出后必须运行 `python <skill目录>/scripts/validate.py <工件根>/<产品名>/05-PRD.md`；
  FAIL 时逐项修复并重跑，**校验器 FAIL 时不得向用户声称 PRD 已完成**。
- 通用红线（任何一步出现即返工）：角色写成"用户"；AC 不可测（"体验更好"）；问题陈述里混进解决方案；
  只写 happy path；模糊词（"较快""灵活""用户友好"）。

## 收尾

Step 08 确认后：提示用户全部工件位置，建议把 `<工件根>/<产品名>/` 提交进 git（文件即交接）。
如果用户中途停止，确保 `_状态.md` 已更新到最新状态再结束。

## 侧边栏同步（文档站存在时必做）

工件写入 `docs/reqs/<产品名>/` 后，若项目有 VitePress 文档站（存在 `docs/.vitepress/config.{mts,ts,js}`），**每完成一步确认后同步更新侧边栏**，否则新工件在文档站上没有入口（菜单漏登记是结构性问题，事后修比随做随登成本高）：

1. **侧边栏挂载点**：`config` sidebar 中为 `'/reqs/'` 路由前缀建/取分组（按产品名分组，组内按 00→07 工件顺序排条目）；不存在该前缀时新增
2. **两种实现方式二选一**：
   - **自动侧栏（推荐）**：`'/reqs/': autoSidebar({ rootDir: new URL('../reqs', import.meta.url).pathname, routePrefix: '/reqs/' })`——工件目录即菜单，新增文件天然有入口，本技能产出后零维护
   - **手写侧栏**：每步确认后把新工件 link 追加到对应产品分组（文件名固定，直接映射）
3. **每步收尾动作**（与更新 `_状态.md` 同一时机）：确认侧边栏含本步产物条目；文档站 dev 在跑时热更新自见，未跑则无需启动
4. **特殊情况**：工件重命名/归并编号调整时，同步修正侧边栏与既有互链（等价于 `sidebar-sync` 的改名处理）；长期未同步的站可整体跑一次 `sidebar-sync` 技能做死链清理
